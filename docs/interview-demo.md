# 辅食搭子：5 分钟面试演示脚本

目标岗位：AI Solution Architect / AI Solutions Engineer  
演示目标：用“小程序服务家长、Web 后台处理问题”的完整链路，证明端到端 TypeScript 交付、AI 工作流设计和安全工程能力。

## 演示前准备

1. 在微信开发者工具中打开项目根目录，进入小程序“今日”页。
2. 启动后台 API：

   ```bash
   pnpm run api:dev
   ```

3. 另开终端启动 Web Console：

   ```bash
   pnpm run web:dev
   ```

4. 浏览器打开 `http://127.0.0.1:4173/support`。

主线只讲一个场景：家长使用 AI 和菜单时发现疑似安全问题，授权提交后由后台完成调查和安全复核。

## 0:00–0:35：一句话说明项目

建议话术：

> 辅食搭子由两个产品端组成。微信小程序帮助家长安排菜单、管理排敏和库存、记录饮食与反应，并提供 AI 问答；React Web 是内部管理后台，用来处理家长上报的问题、验证食物安全规则和观察 AI 质量。两个端通过共享的 TypeScript 安全规则和 contract-first API 连接起来。

不要从 MCP、Trace 或框架名称开始。先让面试官知道谁在用、解决什么问题、为什么需要两个端。

## 0:35–1:35：小程序——家长如何使用

页面：微信小程序“今日”页，可按需打开“AI 搭子”或“记录”页。

指出三个连续动作：

1. 档案与排敏状态决定宝宝当前可以吃什么。
2. 今日菜单、周计划和库存帮助家长完成准备与打卡。
3. AI 搭子通过受限工具读取档案、检查安全、查询食谱或记录反应，而不是直接访问和修改所有数据。

建议话术：

> 这个端解决的是家庭每天真正发生的流程，而不是一个单独的聊天框。AI 可以理解“今天还能吃什么”，但最终食材是否安全由共享规则判断；永久过敏等不可逆状态仍需要家长在界面中确认。

如果时间允许，展示小程序“报告问题”入口：家长选择问题类型，并明确同意后才上传客户端版本、发生时间和可选诊断标识。后台不会收到宝宝姓名、自由备注或完整聊天记录。

## 1:35–2:15：证明安全判断不依赖模型

页面：Web `/safety`

操作：

1. 选择“个体过敏拦截”。
2. 运行确定性检查。
3. 指出 `BLOCK`、规则原因、Trace ID 和 `decisionSource: deterministic-rules`。

建议话术：

> LLM 负责理解问题、选择工具和解释结果；能不能吃由 TypeScript 规则决定。小程序、API 和 MCP 工作流复用同一边界，所以没有模型密钥也能验证安全路径。

## 2:15–3:30：后台——问题如何被处理

页面：Web `/support`

操作：

1. 打开家长提交的关键安全工单。
2. 说明页面只回答三个问题：发生了什么、为什么、下一步做什么。
3. 认领工单，查看自动汇总的诊断上下文和关联 Trace。
4. 记录调查结论并升级安全审核。
5. 切换为安全审核人，记录解决结论。
6. 展示处理时间线。

建议话术：

> 这是小程序用户旅程的后半段。工单带着应用上下文进入后台，支持人员不需要向家长重新索要所有信息。系统只会把真实存在的 Trace、档案版本和菜单日期作为证据；Critical 工单必须升级后由安全审核角色解决。后台可以处理问题，但不能代替家长修改过敏档案。

这里与 SAP Built-In Support 的关联最直接：应用内帮助、问题上报、Case Management 和专家复核被连接成同一条链路。

## 3:30–4:10：后台——如何判断 AI 质量

页面：Web `/observability`

指出：

- Trace 只保存状态、结果计数和规则来源，隐私模式为 `summary-only`。
- 固定安全评测验证该放行的场景和该阻断的场景。
- 9 个合成 agentic 案例验证工具选择、安全阻断和数据来源选择。
- `provider: mock-policy` 明确表示离线结果不是线上模型准确率。

建议话术：

> Trace 用来回答系统调用了什么、规则为什么这样判断；固定评估用来防止后续改动破坏工具选择和安全阻断。真实模型上线后还需要授权数据、人工标注和按模型版本监控。

## 4:10–5:00：用架构图连接 SAP JD

打开 [README](../README.md) 的“两个端如何连接”和“与 SAP JD 的对应关系”。

按业务问题解释技术，而不是报技术清单：

- **Zod + oRPC**：小程序问题上报、后台工单和服务端共享契约，避免前后端字段漂移。
- **React 19 + React Query**：构建管理后台并管理工单、Trace 和评测等服务端状态。
- **Vitest + MSW + Playwright**：从函数和契约测试，一直覆盖到真实 React→API→规则链路。
- **pnpm workspace**：让 contracts、API 和 Web Console 以共享包协作。
- **MCP + Skill + AGENTS.md**：把查档案、检查安全和安全变更流程固化为其他工程师可以复用的 AI 工具，而不是只调用聊天模型。

收尾话术：

> 这个项目证明的是：我可以从家长端体验出发，设计 AI 工具和确定性安全边界，再把问题处理、可观测性和测试补到后台，完成一条端到端 TypeScript 解决方案。当前仍是本地作品集；Docker、Kubernetes、Istio、ArgoCD、真实 OIDC 和生产运维是明确缺口，我不会把它们写成已实现。

## 可选追问

### 为什么还做了多人照护合成场景？

只有面试官追问并发或不可逆变更时，再打开 `/developer/scenarios/collaboration`。它用于证明角色授权、显式确认、乐观并发和菜单重算，不属于 5 分钟主线，也不冒充已经上线的小程序功能。

### 9 个评估案例够吗？

不够代表线上用户分布。它们是可重复回归集；生产还需要授权数据、人工标注、模型版本对比和漂移监控。

### 为什么当前不用数据库？

当前目标是在无付费依赖下证明契约、状态恢复、审计和并发语义。生产环境需要事务数据库和条件更新；单节点文件存储不适合多副本运行。

### 没有待处理工单怎么办？

使用仓库的合成数据，或先从小程序“报告问题”创建一条。不要临时改数据库或跳过授权步骤。
