# 辅食搭子：7 分钟面试演示脚本

目标岗位：AI Solution Architect / AI Solutions Engineer  
演示目标：用一个真实家庭问题证明端到端 TypeScript、AI 工具编排、安全边界、评估和架构取舍能力。

## 演示前准备

```bash
pnpm install
pnpm --filter @fushi/web-console exec playwright install chromium
pnpm run api:dev
```

另开一个终端：

```bash
pnpm run web:dev
```

打开 `http://127.0.0.1:4173/`。家庭协作演示应从档案 v1、鳕鱼“已确认正常”开始。如果此前完成过演示，可为 API 设置新的 `FUSHI_COLLABORATION_STORE_PATH` 后重启。

## 0:00–0:45：先讲业务问题

建议话术：

> 辅食搭子解决的不是“再做一个食谱库”，而是家长每天从档案、库存、排敏、身体状态到实际记录的连续决策。最危险的场景是多人照护：一位照护人发现反应，另一位家长决定是否永久修改过敏档案；这个决定还必须影响后续菜单。

明确边界：

- 微信小程序是家长端产品。
- React Console 是独立作品集和方案验证面，不冒充小程序已上线功能。
- 演示使用 `synthetic-demo` 家庭数据，不包含真实宝宝信息。

## 0:45–2:00：安全规则验证

页面：`/safety`

操作：

1. 选择“个体过敏拦截”。
2. 保留“蛋黄、高铁米粉”。
3. 点击“运行确定性检查”。

指出屏幕证据：

- 总体结论“已触发安全拦截”。
- 蛋黄为 `BLOCK`，并显示规则原因。
- `decisionSource: deterministic-rules`。
- trace ID、延迟和档案快照可见。

建议话术：

> LLM 可以理解问题和解释结果，但不能决定宝宝能不能吃。小程序、API、MCP 和菜单预览共用同一规则边界，因此没有 API Key 也能完整验证安全路径。这是 ADR-0001 的核心取舍。

## 2:00–4:00：多人照护闭环

页面：`/developer/scenarios/collaboration`

操作：

1. 指出初始档案 v1，鳕鱼为“已确认正常”，菜单包含“鳕鱼蔬菜粥”。
2. 切换“只读家人”，提交申请，展示权限拒绝和审计记录。
3. 切回“共同照护人”，提交基于 `reaction-demo-001` 的申请。
4. 指出待确认时菜单仍未变化。
5. 切换为主照护人，先指出确认按钮不可用。
6. 勾选显式确认，再点击“确认并更新安全档案”。
7. 展示档案 v2、永久过敏、鳕鱼食谱被排除、牛肉土豆粥成为替代，以及确认凭证审计。

建议话术：

> 客户端角色不被直接信任，服务端重新绑定身份。不可逆操作需要字面量 true、审计 ID 和主照护人权限。申请与确认还携带 expectedProfileVersion；旧页面会收到冲突而不是覆盖新档案。这是业务安全需求推导出的 RBAC、显式确认和乐观并发，不是为了展示技术名词。

## 4:00–5:15：可观测性与 Agentic Evaluation

页面：`/observability`

指出屏幕证据：

- 安全 trace 只保存数量、状态和结果计数，隐私模式为 `summary-only`。
- 固定安全评测展示 allow/block 对照和阻断召回。
- Agentic 评估展示 9 个合成问题、工具选择、安全阻断、grounding proxy 和端到端成功率。
- `provider: mock-policy` 清楚表明没有调用线上模型。

建议话术：

> 我刻意把 grounding 称为 proxy：它只验证是否选择正确数据来源，不声称回答事实准确。这个评估曾发现 mock 不看工具结果、固定回答“安全”和虚构菜单的问题，随后把 mock 改成结果驱动且证据缺失时拒绝判断。

## 5:15–6:15：工程证据

回到代码或 README，依次指出：

- `packages/contracts/`：Zod + oRPC 单一契约来源。
- `apps/api-server/`：Express handler、领域编排和 OpenAPI。
- `apps/web-console/`：React Query 管服务端状态，Zustand 管本地交互状态。
- `mcp-server/`：23 个工具、10 个资源、3 个提示词。
- `skills/fushi-safety-change/` 与 `AGENTS.md`：把重复的安全开发流程变成团队可复用资产。
- `npm run verify`：API 34/34、React/MSW 23/23、Playwright 2/2、MCP 冒烟 46/46、集成 11/11。

建议话术：

> 我不只是使用 AI 写代码，而是把安全变更步骤固化为 Skill，把架构约束写进 AGENTS.md，把工具路由做成共享资产，再用固定评估和真实浏览器回归保护它。

## 6:15–7:00：生产边界与扩展

主动说明尚未实现：

- React 家庭协作页仍是独立 Web 合成演示，没有进入微信小程序。
- 当前持久化是单节点原子文件，不是生产云数据库。
- 身份是 mock IdP，没有真实邀请和账号体系。
- 离线 100% 不代表线上模型准确率。
- 生产化需要事务数据库、真实身份、多副本一致性、通知、数据删除/导出和线上模型人工评估。

收尾话术：

> 这个项目最想证明的是：我能把模糊的 AI 产品需求拆成体验、工具编排、确定性安全边界、契约、审计和评估，并清楚说明当前证据与生产缺口，而不是只做一个会聊天的界面。

## 常见追问

### 为什么不用 LLM 判断过敏？

概率输出不适合作为安全事实源；LLM 负责理解和解释，确定性规则负责判定。

### 文件持久化为什么不直接换数据库？

当前目标是本地、无付费依赖地证明状态恢复和并发语义。接口已抽象为 store；生产迁移需要事务条件更新，而不是声称文件存储可多副本运行。

### 9 个评估案例够吗？

不够代表线上分布。它是防止固定路由和安全行为回归的第一层；线上还需要授权数据、人工标注、provider 分版本比较和漂移监控。

### 你的个人贡献是什么？

回答时只陈述可证明内容：产品边界、规则优先架构、contract-first API、协作并发与审计、agentic 评估、Playwright 闭环以及开发规范资产。不要把规划项描述成已经生产上线。

## 演示失败时的降级方案

- API 未启动：运行 `pnpm run api:dev`，页面会显示可恢复错误，不用掩盖。
- 无模型密钥：继续演示确定性规则与 `mock-policy`，这是设计支持的离线模式。
- 页面状态已是 v2：更换 `FUSHI_COLLABORATION_STORE_PATH` 后重启 API。
- 时间不足：只演示运营总览、规则验证和 AI 质量三页；家庭确认作为开发者合成场景按需展开。
