# SAP 定向面试追问清单

这份清单用于 5 分钟项目演示后的技术深挖。回答只引用仓库已有事实；“生产化会怎么做”属于方案，不表述成已经完成。

## 1. 请用一分钟介绍这个项目

“辅食搭子面向 4–24 月龄宝宝的多照护者家庭，把档案、排敏、库存、菜单、饮食和反应记录连成一个决策闭环。它最重要的架构约束是 AI 不能决定食物安全，因此我把适用性、过敏状态、尝试窗口和菜单重算做成共享确定性规则，让 LLM 只做理解、编排和解释。工程上我用 pnpm monorepo、Zod/oRPC、Express 和 React 19 做类型安全的端到端实现，再把重复工作固化成 MCP、Skill、AGENTS.md 和离线评估集。多人确认过敏时，还会经过角色权限、显式确认、版本校验和审计，成功后自动替换菜单。”

## 2. 为什么不让 LLM 直接判断宝宝能不能吃？

因为食物安全结果需要可重复、可测试、可审计。模型输出具有概率性，也可能受提示词和上下文变化影响。项目采用 rule-first / LLM-second：模型可以解释“为什么不能吃”或选择读取哪个资源，但最终允许、阻断和菜单替换都由确定性规则决定。这样既使用了 AI 的交互优势，也保留了安全边界。

## 3. contract-first 在这里解决了什么问题？

先用 Zod 和 oRPC 定义输入、输出与错误边界，再实现 handler，React 通过 OpenAPILink 消费同一契约。这样档案版本、显式确认和变更原因等安全字段不会在前后端各写一套；编译期类型与运行时校验同时存在。若新增字段，契约、实现和调用方会一起暴露不一致，而不是等到线上才发现。

## 4. 为什么 React Query 和 Zustand 都要用？

两者解决不同状态。档案、菜单、审计等服务端状态由 React Query 获取、缓存和失效；演示步骤、当前选择等纯本地交互状态由 Zustand 保存。这样避免把远端缓存逻辑复制进全局 store，也避免本地 UI 状态污染 API 数据生命周期。

## 5. 两个照护者同时修改过敏档案会怎样？

申请和确认都携带读取时的 profile version。第一个确认成功后版本递增；第二个使用旧版本提交时返回 `profile-version-conflict`，档案和菜单都不变化，同时留下冲突审计。它防止的是 lost update。当前是单节点演示；生产环境会把版本条件写入数据库事务，例如 `UPDATE ... WHERE version = expectedVersion`，并让档案、审计和菜单事件处于同一事务或可靠事件流程中。

## 6. 为什么需要字面量确认，而不是普通布尔值？

高风险操作使用明确的确认语义，可以防止 UI 默认值、模型自动补参或模糊意图触发不可逆变更。它还让契约和审计更容易说明“谁在什么上下文中授权了什么”。生产环境还应加入重新认证、权限最小化和适当的撤销/纠错流程。

## 7. MCP、Skill 和 AGENTS.md 分别有什么价值？

- MCP 把业务能力暴露为有 schema 的工具、只读资源和提示模板，使 Agent 能在明确边界内调用。
- Skill 把一次安全变更需要遵循的契约、实现顺序、负向测试和交付检查固化成可重复流程。
- AGENTS.md 记录全仓架构不变量、目录责任和质量门禁，使不同 AI coding agent 与人类贡献者遵循同一约束。

它们共同体现的不是“会调用 AI”，而是把重复工作变成团队可以审查、复用和演进的工程资产。

## 8. 9/9、100% 的 agentic 评估意味着什么？

只意味着固定的 9 个离线案例在 `mock-policy` 下全部满足预期，包括工具选择、安全阻断、grounding 代理和端到端流程。它不调用线上模型，也不代表模型回答准确率。若接入真实 provider，我会把评估拆成 deterministic guardrail、tool-call success、task completion、groundedness、latency 和 cost，并按模型、prompt 与数据集版本持续回归。

## 9. 你的测试策略是什么？

按风险分层：共享规则测试确定性业务边界；API 测试验证契约、校验错误和并发冲突；React + MSW 测试页面状态与失败反馈；Playwright 在真实 Chromium 中串联安全规则和多人照护关键流程；MCP 再做单元、冒烟与 11 步集成流程。根目录 `npm run verify` 把这些检查组合成本地质量门禁。当前 API / React 行覆盖率分别为 96.92% / 89.16%，覆盖率只用于防止关键路径被漏测，不替代场景设计。

## 10. 为什么当前使用文件存储？

为了让作品集无云账号也能复现完整业务流程，当前选择单节点原子文件持久化，并明确显示 mock IdP 和合成数据。它适合验证契约和工作流，不适合多副本生产环境。生产化时会迁移到事务数据库，引入真实 OIDC、数据库级并发控制、迁移/备份/恢复、加密与留存策略，并补齐指标、日志、trace、告警和 SLO。

## 11. 如果部署到 SAP 类似的 Kubernetes 环境，你会先做什么？

先区分已经实现的应用能力和待补齐的生产能力。应用侧保留无状态 API 与外置 contracts，把文件状态迁到数据库；交付侧增加容器构建、SBOM/镜像扫描、配置和 secrets 管理、健康检查与资源限制；发布侧建立 GitHub Actions 到 ArgoCD 的可追溯链路；运行侧用 trace ID 串联 API、规则决策和工具调用，并通过 Istio 观测流量、超时和重试。这里是演进方案，不是本仓库已完成的事实。

## 12. 这个项目最能证明你匹配 SAP JD 的地方是什么？

第一，我能在 React 19、Express、oRPC 和 Zod 上做真正的 contract-first 端到端交付。第二，我不仅使用 AI coding 工具，还把安全变更流程做成 Skill，把业务能力做成 MCP，把协作约束写进 AGENTS.md，并用固定评估集回归。第三，我能说明架构取舍和诚实边界，例如为什么规则优先、为什么拒绝过期写入，以及为什么离线 100% 不是线上模型准确率。

## 13. 这个项目与真实生产系统最大的差距是什么？

主要是生产规模和运维证据：当前没有真实多租户身份、云数据库、多副本并发、线上模型评估、SLA、告警和事故处理记录，也没有在本项目中运行 Kubernetes/Istio/ArgoCD。面试时应直接承认，并用其他真实项目证明相关经验；若其他项目也没有，就把它作为明确学习计划，而不是把设计方案说成已交付经验。

## 14. 如果再给你两周，你会优先做什么？

优先完成真实用户价值闭环，而不是增加技术名词：用测试家庭验证“多人确认过敏 → 菜单自动替换 → 所有人看到一致结果”，收集任务完成率、冲突率和纠错需求；工程上把存储替换成事务数据库并接入真实身份，同时保留本地 mock mode。之后再用真实 provider 建立带版本和成本的线上评估基线。
